# 기본 점검 — 설계를 바꾸기 전에 확인한 것 (2026-11-17)

새 학습은 하지 않았다. 코드는 `src/eval/basics.py`(`python -m src.cli basics`)와 `src/agents/rule_agent.py`이고, 결과는 `results/basics/`에 있다. 모든 수치는 8호스트, 스텝 한도 100 기준이다.

## 1. 원리적으로 풀 수 있는 문제인가 → 그렇다

손으로 짠 규칙 에이전트를 만들었다. 이 에이전트는 관측만 읽는다. 미리 아는 것은 어떤 에이전트든 알 수 있는 것뿐이다: 관측 배열의 구조, 행동 목록, 고정된 exploit 표, fragile 규칙. 네트워크의 숨은 상태는 보지 않는다.

행동 순서:
1. 장악한 호스트에서 서브넷 스캔
2. 발견한 호스트에 OS 스캔과 서비스 스캔
3. 맞는 exploit 시도
4. 장악한 호스트의 값이 높으면(목표 호스트) 프로세스 스캔 후 권한 상승

규칙 에이전트도, 네트워크도 결정적이라 네트워크마다 에피소드 1번씩 돌렸다. 출처는 `results/basics/rule_agents.csv`.

| 버전 | 학습 풀 32개 | 테스트 A 30개 | 테스트 B 30개 |
|---|---|---|---|
| 스캔 후 공격 (root를 주는 exploit 우선) | solve 100%, 위반 96.9%, 27.6스텝 | 100%, 93.3%, 24.9스텝 | 100%, 100%, 25.8스텝 |
| 스캔 후 공격 + 범위 밖·fragile 회피 | solve 100%, 위반 0%, 24.0스텝 | 100%, 0%, 22.2스텝 | 100%, 0%, 24.5스텝 |
| 스캔 없이 표 순서대로 시도 | solve 96.9%, 위반 93.8%, 28.6스텝 | 93.3%, 86.7%, 28.6스텝 | 96.7%, 90.0%, 25.1스텝 |

- **관측만으로 모든 네트워크를 풀 수 있다.** 처음 보는 테스트 A·B도 100%다. M1이 테스트 A에서 6~9%만 푸는 것은 문제가 풀 수 없어서가 아니라 학습이 일반화되는 방법을 찾지 못했기 때문이다.
- **비용 0 풀이도 관측만으로 가능하다.** 회피 버전은 세 집합 모두 100% 풀고 비용이 0이다. 단, 이 에이전트는 fragile 규칙을 미리 안다. RL 에이전트는 이 규칙을 비용 신호에서 배워야 한다.
- **보상만 보는 선택은 위반을 부른다.** 스캔으로 정보를 다 가진 에이전트도 root를 바로 주는 exploit을 먼저 고르면 위반율이 93~100%다. 그 exploit이 risky exploit이기 때문이다. 정보 부족만이 아니라 보상 구조 자체가 위반을 끌어낸다.
- 이 규칙 에이전트는 최적이 아니다. 목표가 아닌 호스트도 모두 공격하므로 더 짧은 일반 전략이 있을 수 있다.

## 2. 더 학습하면 테스트 A가 좋아지는가 → 거의 그대로다

저장된 체크포인트는 run마다 마지막 하나뿐이다. 그래서 측정점은 셋이다:
- **0**: 학습 전. 학습과 같은 시드로 초기 가중치를 다시 만들어 평가했다.
- **1M**: 1M run의 마지막 모델.
- **2M**: 2M run의 마지막 모델.

1M run의 학습 로그는 2M run의 앞 1M 스텝과 에피소드 단위로 완전히 같다. 따라서 1M 모델은 2M run의 1M 시점 모델과 같다. 출처는 `results/basics/test_a_over_steps.csv`, 그림은 `results/basics/test_a_over_steps.png`.

| | 0 | 1M | 2M |
|---|---|---|---|
| K=16, 시드 0/1/2 | 3.3 / 2.7 / 1.0% | 8.3 / 8.0 / 1.3% | 8.0 / 6.7 / 3.0% |
| K=32, 시드 0/1/2 | 3.3 / 2.7 / 1.0% | 16.7 / 14.0 / 7.0% | 13.3 / 10.0 / 3.0% |

- 학습 전에서 1M까지 조금 오른다.
- 1M에서 2M 사이에는 K=16은 거의 그대로이고, K=32는 세 시드 모두 조금 떨어진다.
- 그 사이 학습 풀은 거의 100%다.
- 점이 셋뿐이라 중간에 더 높았다가 내려왔는지는 알 수 없다. 알려면 학습 중 체크포인트를 저장하고 다시 학습해야 한다.

## 3. 에이전트는 무엇을 볼 수 있나

NASim이 매 스텝 돌려주는 관측에는 "방금 행동이 보여준 것"만 들어 있다. 우리 `ObsMemory`는 그것을 에피소드 동안 누적한다. 출처는 `results/basics/observation_probe.csv`(실제 네트워크에서 행동을 하나씩 실행해 확인), NASim `envs/state.py`의 `get_observation`, `envs/network.py`의 `perform_action`.

**행동마다 대상 호스트에 대해 드러나는 것:**

| 행동 | 드러나는 것 |
|---|---|
| OS 스캔 | 주소, 도달 가능, 발견됨, OS |
| 서비스 스캔 | 주소, 도달 가능, 발견됨, 서비스 목록 |
| exploit 성공 | 장악 여부, OS, 서비스, 접근 권한, **호스트 값(목표인지 여기서 처음 알 수 있다)** |
| 프로세스 스캔 (장악 후에만 가능) | 접근 권한, 프로세스 목록 |
| 권한 상승 성공 | 장악 여부, 접근 권한 |
| 서브넷 스캔 (장악한 호스트에서) | 연결된 서브넷의 호스트들: 주소, 도달 가능, 발견됨, 처음 발견한 경우 발견 보상 값 |
| 실패한 행동 | 대상 호스트 정보는 없고 결과 플래그 4개만 |

그 밖에 매 스텝 들어 있는 것:
- 직전 행동의 결과 플래그 4개: 성공, 연결 오류, 권한 오류, 미정의 오류
- 호스트마다 범위 밖 여부 플래그 (우리가 추가)

**들어 있지 않은 것:**
- 방화벽 규칙
- 어떤 호스트가 목표인지 (장악하기 전에는 알 수 없다)
- fragile 여부 (OS와 서비스를 보고 추론해야 한다)

**exploit이 실패했을 때 이유를 구분할 수 있나:**

| 실패 원인 | 받는 플래그 |
|---|---|
| 대상이 아직 발견되지 않았거나 도달 불가 | 연결 오류 |
| 방화벽이 그 서비스를 막음 | **권한 오류** |
| OS·서비스가 exploit과 맞지 않음 | **권한 오류** |
| 공격 근거지로 쓸 장악 호스트가 없음 | **권한 오류** |
| 확률적 실패 | 미정의 오류. 이 설정에서는 모든 exploit 성공 확률이 1이라 일어나지 않는다 |

- **방화벽 차단과 "잘못된 exploit"은 같은 플래그(권한 오류)로 나온다.** NASim은 원격 권한 검사(`has_required_remote_permission`) 안에서 방화벽을 먼저 보고, 막히면 권한 오류를 낸다. 연결 오류를 내는 방화벽 검사(`traffic_permitted`)는 그 뒤에 있는데, 호스트 방화벽이 비어 있는 이 설정에서는 사실상 도달하지 않는다.
- 그래서 에이전트가 방화벽을 알아낼 방법은 소거법뿐이다. 스캔으로 OS·서비스를 확인해 맞는 exploit을 골랐는데도 권한 오류가 나면 방화벽(또는 근거지 부족) 때문이다. 스캔하지 않고 시도한 exploit이 실패하면 원인을 알 수 없다.

## 4. 보상 구조 — 무작정 시도하는 게 스캔보다 싼가

출처는 `results/basics/costs_rewards.csv`, `results/basics/blind_vs_scan_attempts.csv`.

- **비용:** 모든 행동이 1이다. OS 스캔, 서비스 스캔, 서브넷 스캔, 프로세스 스캔, exploit 5개, 권한 상승 2개 모두.
- **보상:**
  - 목표(민감) 호스트에서 처음 root를 얻으면 +10. 목표는 2개라 합계 20.
  - 다른 호스트에서 처음 root를 얻으면 +1.
  - 서브넷 스캔으로 새 호스트를 발견하면 하나당 +1.
- 한 스텝의 보상은 (얻은 값 − 행동 비용)이다. 안전 비용(C1·C2)은 보상에 들어가지 않는다.

**호스트 하나를 처음 장악하는 데 드는 행동 수 (방화벽은 무시, 학습 풀 호스트 전체):**
- 무작정 표 순서대로 시도: 평균 2.24번 (최소 1, 최대 5). 호스트당 맞는 exploit이 평균 1.33개다.
- 스캔 2번 후 맞는 exploit 1번: 항상 3번.

→ 호스트 하나만 놓고 보면 **무작정 시도가 평균 0.76행동 싸다.**

**실제 에피소드 전체에서는 반대였다** (규칙 에이전트, 평균 return):
- 무작정 시도: 0.19 / −0.40 / 3.47 (학습 / A / B)
- 스캔 후 공격: 2.31 / 4.50 / 4.33

방화벽에 막힌 실패를 구분하지 못해 시도가 늘고, 일부 네트워크는 풀지 못했기 때문이다. 다만 이 비교는 내가 짠 규칙 구현 하나에 대한 결과다.

**가장 중요한 비교** (M1, 2M 스텝, 학습 풀 평가):
- 외운 M1: 약 8스텝에 return 약 20 (K=16 20.0, K=32 19.6)
- 일반적으로 동작하는 규칙 에이전트: 같은 학습 풀에서 약 24~28스텝에 return 2~4
- 보상만 보면 **외우는 정책이 일반 정책보다 학습 네트워크에서 약 16점 높다.** 차이는 거의 전부 행동 수다. 일반 정책은 스캔해야 하고, 목표가 어디인지 모르므로 여러 호스트를 장악해 봐야 한다.

## 이것이 뜻하는 것

1. 문제는 풀 수 있다. 관측만으로 100% 풀리고, 비용 0 풀이도 존재한다. 환경이나 관측에 결함이 있어서 일반화가 안 되는 것은 아니다.
2. **학습 목표가 외우기를 선호한다.** 네트워크 수가 16~32개면 에이전트는 초반 관측(첫 exploit이 보여주는 DMZ 호스트 구성 등)으로 어느 네트워크인지 알아낼 수 있다. 그 네트워크 전용 최단 경로를 실행하면 일반 전략보다 보상이 훨씬 높다. PPO는 학습 풀의 보상을 최대화하므로 일반화하지 않는 쪽이 정답이다. 학습을 더 해도 테스트 A가 좋아지지 않은 것과 맞는다.
3. 따라서 "학습을 더 하면 나아진다"는 기대하기 어렵다. 일반화가 생기려면 외우기가 불가능하거나 손해가 되어야 한다. 예를 들어 네트워크 수를 크게 늘리거나 에피소드마다 새 네트워크를 생성하는 방식, 또는 외워도 소용없을 만큼 네트워크 간 공통점을 늘리는 방식이다. 어느 쪽도 아직 시험하지 않았다.
4. **H4 해석에 주의할 점:** 방화벽 차단과 잘못된 exploit이 같은 플래그라 스캔의 정보 가치가 일부 있다. 하지만 외운 정책은 스캔이 전혀 필요 없으므로, 학습 풀에서 "스캔 없이 exploit"이 많은 것은 위반 원인이라기보다 외우기의 결과일 수 있다.
5. **RQ1 해석에 주의할 점:** 정보를 다 가진 규칙 에이전트도 root를 바로 주는 exploit을 고르면 위반율이 90%를 넘는다. 보상과 안전이 실제로 충돌하도록 만든 설계가 의도대로 동작하고 있다는 뜻이다.
